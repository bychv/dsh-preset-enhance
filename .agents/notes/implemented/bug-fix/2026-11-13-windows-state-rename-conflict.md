# 修复 Windows 状态文件替换冲突与请求全量写盘

Status: implemented

## 问题与证据

报告涉及 0.3.7-rc.1。修复前的状态存储和请求写入路径与该标签一致。默认状态文件在 `DSH_HOME/preset-enhance/state.json`，显式 `dataFile` 可以覆盖。它不按 profile 名称分隔，两个宿主进程如果解析到同一路径就会共享数据。原报告在本地忽略的 `sample/err_report.txt`，不随仓库或发布包分发。见[状态存储](../../../../src/lib/store.mts)、[请求注入入口](../../../../src/index.mts)和[架构说明](../../../../docs/ARCHITECTURE.md)。

1. `writeStateFile` 先写同目录下唯一命名的临时文件，再用 `rename` 原子替换。目标被不允许删除共享的句柄持有时，本机 Windows 实测替换抛出 `EPERM`。原文件字节完整，失败后完整临时文件残留。该错误发生在请求准备阶段，`llm/stream` 记录失败快照后继续抛出，模型尚未收到请求。
2. `wantsPreset || catalogChanged` 成立才进入注入事务。现有事务无条件写盘，`prior.key === key` 命中后提前返回也会全量写入。即使本次不启用预设，工具目录变更仍可能进入写路径。首次自动绑定与工具目录确有变更时，即使编译命中也要保存。宏变量和编译记录更新时不一定递增编辑用 `revision`，因此不能用它判断磁盘是否需要写入。
3. 写队列用 `globalThis` 和已解析路径在单个 Node 进程内协调，覆盖同进程不同插件实例及热重载。跨进程时两个读改写可读取同一旧快照，再依次成功替换，最后写入者覆盖前一次更新。替换的原子性只保护读取者看到完整 JSON，无法保护完整的读改写事务。
4. 报告状态文件约 50.85 MB，其中 `sessions` 约 40.9 MB。编译记录每个会话保存一份，其中包含编译后的历史和提示词，当前没有按容量淘汰。这会增加解析、序列化、复制、写入和临时文件成本，也增加反复替换的次数。小文件也能复现冲突，现有对照不足以量化体积与单次 `rename` 失败概率的关系。

本次在 Windows、Node v24.22.1 上用虚构预设和隔离文件做了两组验证：

- 运行真实插件的 `llm/stream` 钩子，使用假宿主派发函数并禁止外部 HTTP。用 `FileShare.Read` 持有目标文件时，同一历史的缓存命中和改动历史后的未命中均报 `EPERM / rename`，派发次数为零。命中留下与原文件字节相同的临时文件，快照显示“准备失败，未发送”。解锁后相同输入成功派发，局部、全局计数均保持 1，没有再执行一次计数宏。
- 两个 Node 子进程各用真实 `PresetStore` 对同一文件写不同全局键。同步到两者都读完 revision 17 后，先让 A 完整提交，再放行 B。两次都成功且替换不重叠，最终只剩 B 的键，revision 为 18，正确保留两次更新应为 19。

报告的双写者试验另观察到实际 `EPERM`。本次未在真实用户状态上运行压力脚本，也未追踪历史故障当时的冲突句柄。单写者对照零失败只能说明试验期间未触发，无法排除历史上的索引器、同步程序或其他进程。

## 决定

- 只有工具目录、会话绑定或宏等持久化状态变更才提交请求事务。缓存命中和纯编译都跳过 JSON 替换。工作台编辑仍等待实际提交，失败时保留原状态。提交成功才更新观察者。正文正则的会话深度刷新改由请求准备通知触发。
- 状态和 Chat 附件索引共用[原子文件工具](../../../../src/lib/atomic-file.mts)。Windows 替换遇到 EPERM、EACCES 或 EBUSY 时，以 20、40、80、160 ms 间隔重试同一个文件。失败后尽力删除本次临时文件。不会重新运行事务回调、宏或外部 resolver。
- 用每个 JSON 文件旁的 `*.write-lock.sqlite` 对整个读改写加锁。SQLite 文件只作锁载体，不写用户数据，不切换存储格式。状态锁等待上限 2 秒，附件索引保留 10 秒。锁竞争以异步等待处理，进程退出后系统释放锁。锁文件固定保留，防止不同进程打开不同文件。目标路径经过 realpath 解析。协调范围是同一路径上使用新实现的进程，升级和回退前要停止同路径旧进程。
- 新版临时文件使用 `<文件名>.write-<UUID>.tmp`，取得相同写锁后可清理崩溃残留。状态存储在启用和有请求的维护间隔内检查，附件索引在写入时检查。旧版 `<文件名>.<UUID>.tmp` 仅回收超过 24 小时的匹配文件。其他文件及目录不参与清理。清理失败记录日志并保留原错误。

## 会话数据迁移与兼容

`state.json` 仍为版本 1。启动维护时从旧会话编译记录提取 `presetId`、`result.local` 与旧编译键，在同一次原子提交中移除请求历史和重复全局变量。若替换失败，当前进程仍可读旧文件，后续真实提交会应用精简布局。宏持久化失败时停止本次准备，工作台显示错误。由同一 JSON 提交同时保护局部和全局宏变量、绑定及工具配置。

[会话编译缓存](../../../../src/lib/session-compilation.mts)以 64 个会话和 16 MiB 序列化体积为上限。工作台最近实际请求仍由原有[请求快照](../../../../src/lib/request-preview.mts)提供。缓存失效或重启后，若准备键匹配最后一次已提交的宏操作，使用变更前的键值重放本次编译，跳过再次提交。旧格式未保存宏操作前的值，迁移后按现有值重新渲染同一输入，持久化的局部、全局值保持不变。回退至旧版本时仍可读取局部变量，旧版会从下一次请求重新编译，其写入和去重行为也恢复为旧版。协议、绑定、预填充目标和附件素材来自本次事务确认的预设。详见[状态类型](../../../../src/lib/types.d.mts)和[工作台指南](../../../../docs/guides/WORKBENCH.md)。

未采用直接覆盖、先删再替换或只锁 rename。前两种会破坏读取原子性，后者无法防止旧快照覆盖。继续用 JSON 保留导入及回退路径，避免为消除缓存体积引入跨文件提交或迁移全部数据。

## 验证

- Windows 真实不共享删除句柄下，同一请求重放正常派发，磁盘提交数为零。不同输入触发需要写入的宏时，持续锁定使提交失败，文件内容和计数保持原值，无新临时文件。短锁释放后写入成功，计数只增加一次。
- [存储生命周期](../../../../tests/store-lifecycle.test.mjs)覆盖双进程保留两次更新、进程退出自动释放锁、旧状态精简、残留回收及同进程热重载事务行为。[核心回归](../../../../tests/core.test.mjs)覆盖无变化请求不提交、插件重新加载后宏不重复累加。[Chat 适配器回归](../../../../tests/chat-adapter.test.mjs)覆盖附件索引持久化及固定锁文件。类型检查、构建和 643 项回归通过。
- DSH 0.2.2-rc.2 alpha 槽位以独立状态文件和本地假接口完成 12 次请求。验证系统模板分段、工具执行续轮、草稿预览和真实宿主附件入库。纯编译没有写入会话历史。未调用外部模型。
