# 捕获写在思维链里的工具调用

Status: implemented

## 问题

用户于 2026-10-07 提供截图：思考区域中出现结束思考标记和完整的 DSML calls / invoke / parameter 文本，但调用没有转成实际工具调用。案例目标是 glob，参数 pattern 为星号。调用不能因为出现在思维链里而漏掉，也不应要求它必须位于正文的 content 标签内。

截图不是原始响应，无法确认竖线码点、真实分片与结束事件，因此当时不把视觉转录当作精确复现。后续在沙盒用真实调用定位到了两类可复现的失效。

## 决定

以下修改都在已发布的工具兼容转换里，路径为 [toolcall-prefill](../../../../src/lib/toolcall-prefill.mts)。两条通道共用同一套调用识别规则，正文、思维链以及提取器重新判定归属的文本都送入同一个解析器：

- 开启正文/思考提取（extractOutput）时，提取器判定为思考的文本原先被原样透传，从未做调用识别。现在这段文本与原生思维链走同一条识别规则，完整调用转为工具调用并从可见通道移除。
- 流在最后一块 delta 之后直接结束、既无 finish_reason 也无 [DONE] 时，原先不会进入终结分支，缓冲区内容被当文本倒出。现在流结束时统一排空提取器、影子缓冲与两个解析器，把已缓冲的完整调用以 finish_reason `tool_calls` 交付。
- 识别不依赖换行：wrapper、invoke 与各 parameter 紧邻、多参数同行、无 wrapper 仅 invoke、逐字符分片均可识别，已由测试固定。

边界沿用既有完整性规则：无法证明完整的标记（截断的 wrapper、未闭合的 parameter）不生成调用，仍作为文本呈现；错误事件与取消不生成调用。同一调用重复出现在正文与思维链时按出现次数去重，同一通道内连续两次同参数调用分别保留。

不包含：扩展新的标记方言、改变正文/思考提取策略、或要求模型只在正文输出调用。

## 考虑过的替代方案

**要求模型只在正文输出工具调用。** 可在提示词中建议，但无法解决模型已经把完整调用写进思维链的情况，本次真实调用也证实模型会这样做。

**只放宽正则。** 近似样本在纯解析层面本来就能通过，说明失败不在标记识别范围，而在通道与结束路径。放宽匹配会误捕获说明文本或残缺片段。

**等整个响应结束后统一扫描。** 可作为结束时的兜底，但会牺牲正文与思考的流式效果，因此只用于流结束时的排空，不替代增量处理。

## 影响与验证

代码路径：[宿主桥接](../../../../src/lib/deepseek-beta.mts)在启用工具仿真或正文提取时挂载 responseTransform，流式与非流式分别由 transformToolCallResponse 与 transformToolCallJson 处理。

测试：[toolcall-prefill 测试](../../../../tests/toolcall-prefill.test.mjs)新增正文与思维链双路径、逐字符分片、无 finish_reason 的 EOF、正文与思维链同调用去重、相邻同参数调用、截断不伪造、以及无换行形态（含非流式与提取开启）等用例；[正文提取测试](../../../../tests/output-extractor.test.mjs)补充提取路径的调用捕获。全量 536/536 通过，构建干净。

真实调用验证：沙盒 alpha 槽位，模型 deepseek-flash，beta 端点，末条 assistant 带 prefix:true（前缀续写），开启工具仿真与正文提取。同一份真实响应字节分别经过修改前后两个版本：

- 修复前：捕获 0 个调用，finish_reason 为 stop，调用文本残留在思考通道。
- 修复后：捕获 1 个调用，名称为 issue_time_token 或 get_current_time，参数正确，finish_reason 为 tool_calls，两个可见通道均无调用文本。

另做端到端往返：捕获到的调用被真实执行（工具有副作用，写出令牌文件），结果回灌后下一轮模型使用了该结果。要求模型把调用压成一行、仅写在思考区不切出时，结果同样成立。

未覆盖：真实流量只出现紧凑的 DSML 方言与官方信封之外的少数形态；reasoning_content 字段内直接出现调用文本这一入口未在真实调用中复现出差异，仅有纯函数与流式测试覆盖；未在真实 DSH 会话控制器内跑完整链路，端到端验证止于转换器加真实工具执行与续轮。
