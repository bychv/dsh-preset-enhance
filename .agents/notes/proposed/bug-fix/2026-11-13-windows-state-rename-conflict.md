# 修复 Windows 状态文件替换冲突与请求全量写盘

Status: proposed

## 问题与证据

报告涉及 0.3.7-rc.1。当前分支的状态存储和请求写入路径与该标签一致。默认状态文件在 `DSH_HOME/preset-enhance/state.json`，显式 `dataFile` 可以覆盖。它不按 profile 名称分隔，两个宿主进程如果解析到同一路径就会共享数据。原报告在本地忽略的 `sample/err_report.txt`，不随仓库或发布包分发。见[状态存储](../../../../src/lib/store.mts)、[请求注入入口](../../../../src/index.mts)和[架构说明](../../../../docs/ARCHITECTURE.md)。

1. `writeStateFile` 先写同目录下唯一命名的临时文件，再用 `rename` 原子替换。目标被不允许删除共享的句柄持有时，本机 Windows 实测替换抛出 `EPERM`。原文件字节完整，失败后完整临时文件残留。该错误发生在请求准备阶段，`llm/stream` 记录失败快照后继续抛出，模型尚未收到请求。
2. `wantsPreset || catalogChanged` 成立才进入注入事务。现有事务无条件写盘，`prior.key === key` 命中后提前返回也会全量写入。即使本次不启用预设，工具目录变更仍可能进入写路径。首次自动绑定与工具目录确有变更时，即使编译命中也要保存。宏变量和编译记录更新时不一定递增编辑用 `revision`，因此不能用它判断磁盘是否需要写入。
3. 写队列用 `globalThis` 和已解析路径在单个 Node 进程内协调，覆盖同进程不同插件实例及热重载。跨进程时两个读改写可读取同一旧快照，再依次成功替换，最后写入者覆盖前一次更新。替换的原子性只保护读取者看到完整 JSON，无法保护完整的读改写事务。
4. 报告状态文件约 50.85 MB，其中 `sessions` 约 40.9 MB。编译记录每个会话保存一份，其中包含编译后的历史和提示词，当前没有按容量淘汰。这会增加解析、序列化、复制、写入和临时文件成本，也增加反复替换的次数。小文件也能复现冲突，现有对照不足以量化体积与单次 `rename` 失败概率的关系。

本次在 Windows、Node v24.22.1 上用虚构预设和隔离文件做了两组验证：

- 运行真实插件的 `llm/stream` 钩子，使用假宿主派发函数并禁止外部 HTTP。用 `FileShare.Read` 持有目标文件时，同一历史的缓存命中和改动历史后的未命中均报 `EPERM / rename`，派发次数为零。命中留下与原文件字节相同的临时文件，快照显示“准备失败，未发送”。解锁后相同输入成功派发，局部、全局计数均保持 1，没有再执行一次计数宏。
- 两个 Node 子进程各用真实 `PresetStore` 对同一文件写不同全局键。同步到两者都读完 revision 17 后，先让 A 完整提交，再放行 B。两次都成功且替换不重叠，最终只剩 B 的键，revision 为 18，正确保留两次更新应为 19。

报告的双写者试验另观察到实际 `EPERM`。本次未在真实用户状态上运行压力脚本，也未追踪历史故障当时的冲突句柄。单写者对照零失败只能说明试验期间未触发，无法排除历史上的索引器、同步程序或其他进程。

## 第一阶段：减少写入并处理瞬时冲突

- 让请求事务显式区分“有持久化变更”和“仅返回编译结果”。从同一个串行事务中判断最终状态，避免在外部用旧快照决定跳过。缓存命中且没有绑定或工具目录变更时跳过写入。未命中时分别跟踪宏、绑定、工具目录和编译缓存的变化。普通编辑事务可保持默认提交，避免所有调用者都依赖手动标记。不要为判断变化再序列化两份大状态。
- Windows 替换阶段对已确认可重试的错误，例如本报告中的 `EPERM`，用短退避和明确的总上限重试同一临时文件。重试不重新运行事务回调、宏或动态模板，不把 JSON 解析、权限、磁盘满等故障一律当成瞬时冲突。仍使用同目录原子替换，避免先删目标、直接覆盖或复制兜底。失败时尽力删除**本次**临时文件，保留原始异常，清理失败另行报告。
- 失败语义按写入内容处理。仅用于缓存和请求诊断的数据移出必需的磁盘提交路径，保存不了这类数据时仍用已准备的请求发送。显式编辑、绑定与需要提交的宏变量按事务确认结果，失败时保留草稿或给出可重试的明确错误。涉及宏变量时避免请求已经使用新值、后续读取却回到旧值。暂不采用全局内存 dirty 状态，也不悄悄以旧快照覆写磁盘。只有确认提交后才发布持久化观察通知。仍需刷新本次请求用到的工具策略和显示正文深度，不能把跳过磁盘写入等同于跳过所有运行时通知。
- 保留按路径队列以及 `close/drain`、取消和热重载行为。等待磁盘短重试时不重新启动外部 resolver。已有孤儿临时文件另行处理，不能启动时批量删除可能属于其他活跃写者的文件。

## 第二阶段：拆出可重建内容

保留预设、资源库、会话绑定、工具策略、`state.global` 和会话局部宏变量。现有 `sessions[id].result.local` 是后续请求、草稿预览和正文正则的输入，需要迁到带 `presetId` 的独立持久化字段。切换绑定、删除预设或迁移旧记录时延续变量归属规则，兼容空记录和部分旧字段。不要将旧编译结果内的 `result.global` 回填覆盖顶层全局值。

`messages`、`entries`、前缀判定和编译诊断可放在有会话数及字节上限的运行时缓存。工作台的 `last` 和 `protocolNotes` 需改由该缓存供给或随实际请求快照读取，实际出站 Raw 继续走既有有界快照。正文正则从持久化局部变量读取，使用会话历史更新及相应通知重新计算深度，避免依赖空事务写盘。见[状态类型](../../../../src/lib/types.d.mts)、[请求快照](../../../../src/lib/request-preview.mts)、[正文显示配置](../../../../src/lib/display-config.mts)及[显示客户端](../../../../packages/display-regex/src/client/runtime.mts)。

旧缓存命中同时跳过宏副作用，删除缓存会影响 `incvar`、`addvar` 等有状态宏。迁移前明确同一准备结果的复用语义，活跃请求和传输重试复用原产物，失败未提交不得被标为已处理。若要求重启或缓存淘汰后仍识别相同输入，需要将轻量的已提交记录与局部、全局变量一起提交，或采用等效的可恢复方案。区分用于复用渲染结果的输入依赖与用于去重副作用的标识，不能直接把已有编译键当成跨版本幂等键。异步模板依然在事务外执行，提交时继续校验有效绑定、预设、变量和历史是否变化。见[宏求值](../../../../src/lib/macros.mts)和[动态模板契约](../../../../docs/api/TEMPLATE_API.md)。

迁移应从旧版本完整提取局部变量，再于一次成功的原子提交中清除可重建内容。重复迁移不重复执行宏，不读取损坏文件为初始空库。旧版是否可回读须验证，若布局不兼容则给出备份及回滚办法。减少单文件体积后实测长历史场景的文件大小和写入次数，再决定是否需要分文件或数据库。

## 同一路径的跨进程约定

跨进程冲突须单独处理。部署只支持单写者时，应在共享同一文件的场景明确拒绝第二写者，或为不同宿主配置独立 `dataFile`。需要支持共享库时，对同一规范化文件路径协调完整的“读→校验→修改→替换”区间，并验证退出和崩溃恢复、路径别名及热重载。只锁 `rename`、只看全局 revision 或延长重试时间都挡不住已经从旧快照算出的覆盖写。锁需要确认归属后释放，不能用超时直接删除仍活跃的锁。

按会话分文件可以降低单次写入体积，但会增加全局变量、局部变量与绑定的一致性成本。SQLite/WAL 能提供事务边界，若实际需要共享写入再评估迁移、打包与文件系统适用性。`ReplaceFileW` 也受目标句柄共享模式限制，因此本轮沿用现有原子替换。

## 验收

- Windows 用隔离目标文件和真实不共享删除的句柄。锁内的无变化缓存命中应正常派发，且不触发替换或留下临时文件。短锁释放后变更提交成功且宏只执行一次。锁持续到重试耗尽时，原 JSON 完整，显式编辑收到失败，后续事务仍可成功。并覆盖不应重试的错误和清理失败。
- 两个独立进程同路径写不同键。按支持策略保留两次更新，或明确拒绝第二写者。不能出现两次成功而丢一次更新。验证旧实例关闭后新实例可继续写入。
- 从含长历史的旧文件迁移并重启，检查预设、绑定、全局及局部宏变量、编辑冲突检测和正文正则仍有效。验证缓存命中、未命中、淘汰、工具续轮、传输重试和异步解析取消，观察保存次数及状态体积。Raw 仍反映实际发送数据。
- 复用[存储生命周期](../../../../tests/store-lifecycle.test.mjs)、[动态请求](../../../../tests/dynamic-request.test.mjs)、[正文生命周期](../../../../tests/display-lifecycle.test.mjs)和[启动恢复](../../../../tests/startup-recovery.test.mjs)测试。实现后从源码构建，用隔离 DSH 和本地假接口跑一次完整请求。本次只确认现有行为并记录方案，验收项待实现。
