# DSH 压缩与预设请求处理的兼容边界

Status: proposed

本记录的分析基线为 next-ver / `ec559bb`；当前项目目录可能位于其他分支，实施前先核对差异。指向该基线源码的链接不代表当前分支已有相同文件。

## 问题

DSH 会压缩当前可见聊天历史，插件则在模型请求阶段注入提示词、处理历史和变量。两者操作的层次不同，需要确认压缩能否正确继续会话，以及哪些预设状态不应被压缩或重试改变。

结论：**基础链路可以衔接，但不能认为完全无影响。** 摘要请求已有用途旁路；预设本身不会被删除，后续请求会读取压缩后的历史。但检查点身份、重试变量副作用、输出预算以及仅存在于请求中的上下文有明确边界需要处理。

本笔记是分析与修复提案，未实施下面的修复。

## 检查基线与证据

- 插件：next-ver，已发布代码提交 `ec559bb`（0.3.5-alpha.1）；本地另有图标和 agent 文档改动，不影响此分析。
- 宿主：alpha 槽位 npm `0.2.1-alpha.1`；源码提交 `5badb15009ae1756c3afe0ae0cef1faafc290ccc`，不是对未来 master 的保证。
- 检查方式：源码追踪及虚构数据的纯函数复现。没有请求模型、启动沙盒、触发真实压缩或修改会话状态。

上游代码以固定提交为准：

- [摘要请求与提示词](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/packages/compaction/compaction-basic/src/summarizer.ts)：使用同一 sessionId，设置 purpose 为 compaction；追加摘要指令并保留文本结果。
- [选取范围及提交检查点](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/packages/compaction/compaction-basic/src/region.ts)：保护工具调用/结果配对边界，从当前 surface 派生摘要输入，以 user 角色的 compact-checkpoint 替换选定范围。
- [自动压缩与溢出重试](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/packages/compaction/compaction-basic/src/index.ts)：在 pre-step 检查压力，也在上下文溢出后压缩并重试；输出预留来自 requestHeader 或适配器默认值。
- [宿主请求头生成](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/packages/core/agent-loop/src/agent.ts)与 [token 计量](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/packages/llm/token-meter/src/index.ts)：请求头在流式中间件改写前形成；估算基于 surface，可用实际 usage 作后续锚点。

## 已有保护

1. [请求入口](https://github.com/bychv/dsh-preset-enhance/blob/ec559bb14d67c1443ce98599804171e0d27b873b/src/index.mts)的 injectStream 遇到 options.purpose 直接放行。因此常规摘要请求不重新编译预设，不运行动态解析器，也不主动套用预填充或覆盖预设变量。
2. 编译输入采用本次 options.messages，草稿预览采用 deriveMessages。压缩完成后使用检查点及保留尾部，不主动从原始事件日志复活被替换的旧历史。
3. 编译缓存包含输入消息；压缩改变消息时会失效。预设定义、会话绑定及变量保存在插件自己的状态中，宿主压缩不会直接删除它们。
4. 工具结果裁剪与图片卸载由宿主维护投影；插件应继续接受投影后的消息，不恢复被裁剪的内容。原生压缩保证的工具配对边界仍应保留。

这些保护不等于所有层都能识别摘要用途，尤其不覆盖下述底层 fetch 桥的并发匹配。

## 影响与修复建议

### 1. 检查点被当成用户输入或可编辑的普通历史

**已确认行为。** [宏编译](https://github.com/bychv/dsh-preset-enhance/blob/ec559bb14d67c1443ce98599804171e0d27b873b/src/lib/preset.mts)和[动态解析](https://github.com/bychv/dsh-preset-enhance/blob/ec559bb14d67c1443ce98599804171e0d27b873b/src/lib/dynamic-templates.mts)寻找最后一条 user 时，没有排除 compact-checkpoint。如果摘要之后没有保留真实用户消息，lastusermessage、latestUser 和 userText 会得到摘要。普通请求中有保留用户消息时不会触发这一条件。

[历史修改](https://github.com/bychv/dsh-preset-enhance/blob/ec559bb14d67c1443ce98599804171e0d27b873b/src/lib/history-patches.mts)仅保护工具结果，允许 replace-text/append-text 指向检查点；提示词正则同样没有专门的检查点边界。宽泛规则或按固定深度写入可能改坏摘要。

**建议：** 统一按 source.kind 识别检查点，不能通过正文里的标签字符串猜测。最新用户输入选择排除检查点，但完整 history 仍保留它供模型和历史型解析器读取。默认禁止对检查点做破坏性文本修改、跳过普通用户输入正则；深度插入仍可发生在其前后。若未来需要显式处理摘要，再增加清晰的独立能力，不静默改变其身份。

深度坐标仍以本次可见历史计数；压缩前后的 depth 不保证指向同一条原消息。超界替换继续报错，不回读旧日志补齐。接口文档需说明这一点。

### 2. 压缩重试再次执行有副作用的宏

**已确认编译行为，宿主端到端待验证。** 请求编译后立即把 local/global 写入状态，发生上下文溢出时模型未成功返回。压缩替换历史后缓存键改变，再编译使用上一次已提交的变量，因此 incvar/addvar 等可能重复生效；动态提供者也会再次运行。

纯函数复现：初始编译 incvar::count 得到 1，携带第一次 local 重新编译得到 2。并非每次压缩都存在此问题：首次请求之前的正常 pre-step 压缩，不等于失败请求的重试。

**建议：** 将“重新生成请求内容”和“提交变量副作用”分开。用宿主可验证的逻辑请求身份区分同一轮同一步的失败重试、工具续步和新用户轮次。同一步压缩重试从首次编译前的变量基线重算，只提交一次副作用；不复用旧消息结果，否则会恢复未压缩历史。工具续步是否累加保持既有语义，不用 sessionId 或用户文本作为唯一去重键。

实施前先确认宿主提供的 turn/step 或等效请求身份；避免在并发全局变量更新下直接回滚整个 global 对象。动态解析器明确可被重试调用，外部不可逆动作应由提供者按逻辑请求身份去重。

### 3. max_tokens 和注入正文不完全进入压缩预算

**源码确认计量层次不一致；实际偏差需集成测量。** 插件在 llm/stream 后段才覆盖 maxTokens，并可在 fetch 层改 max_tokens；压缩服务读的是先前持久化的 requestHeader。用户设置的输出预留可能没有进入宿主压缩阈值。预设正文、DSML 工具说明和历史改写也并非 surface 本身的内容。

不能简单断言宿主永远漏算：成功响应的 usage 可以反映实际请求体，并成为后续计量锚点。但首轮、刚切换大预设、动态内容变大或没有可用 usage 时仍可能低估；已有 usage 也不能保证跟踪之后注入量的变化。

**建议：** 优先把启用预设的 maxTokens 接到宿主 agent/request 配置阶段，使请求头、输出预留和实际发送一致；保留旧宿主必要的传输兜底，不能手写伪造 request/header。注入正文的预算另行核对宿主是否有可用扩展点，先用无副作用的已准备结果计量，不为估算额外运行动态解析器。没有可靠扩展点时明确限制，并保留溢出压缩重试。

如果固定预设与工具说明本身已超过可用窗口，压缩历史无济于事，应给出明确错误，避免反复压缩或静默裁掉提示词。

### 4. 摘要不是插件实际发送内容的完整重放

**源码确认。** buildSummarizationInput 从 surface 系统头和选定事件派生消息，工具取 requestHeader；它不读取插件的最终 Raw。仅在请求中注入的动态事实、历史替换结果和自定义系统模板不会自动进入摘要。压缩后静态预设会重新注入，但依赖已被压掉的原消息才能生成的动态事实可能无法恢复。

此外，上游摘要指令偏向英文编程任务。角色叙事或其他酒馆用途的细节保留效果不能仅凭代码保证；这是质量风险，不是已复现的数据丢失结论。

**建议：** 稳定事实由提供插件持久化并在后续请求重新注入，不把请求局部修改当成记忆存储。确需压缩这些内容时，另做受控摘要上下文扩展，复用已准备的只读事实，而不是把整份预设和 assistant 前缀灌入摘要。自定义摘要格式应作为后续独立能力，先验证实际需求。

关闭 DSH 提示词只控制普通预设请求，当前并不控制宿主内部摘要的系统头；不要向用户承诺摘要调用同样完全按预设运行。

### 5. 同会话辅助请求可能误用活跃的 fetch 设置

**匹配机制已复现，并发可达性待验证。** [兼容桥](https://github.com/bychv/dsh-preset-enhance/blob/ec559bb14d67c1443ce98599804171e0d27b873b/src/lib/deepseek-beta.mts)按会话及前缀激活；请求参数存在同会话 fallback，fetch 本身看不到 options.purpose。只要该会话仍有活跃配置，另一条无预填充的辅助请求也可能被覆盖 stream/max_tokens。

纯函数复现使用真实头名 x-deepseek-harness-session-id：活跃条目设置 1234/false，辅助请求原为 8192/true，改写后成为 1234/false。普通压缩通常在主请求收尾后执行，不能据此声称每次压缩都会误改；需要验证调用顺序、并发与清理路径。

**建议：** 将桥接设置绑定到具体请求的异步作用域，显式携带正常请求或辅助用途，覆盖整个异步迭代过程。辅助请求必须隔离外层激活，不能只在 injectStream 提前 return。沿用现有请求追踪思路，避免再增加一个凭文本匹配的旁路规则。

## 方案与实施顺序

1. 先补检查点分类、最新用户选择及摘要保护，明确深度语义。
2. 将 maxTokens 提前到宿主请求配置，并验证摘要用途仍独立。
3. 建立逻辑请求重试身份与变量副作用去重；同时补同会话请求级桥接隔离。
4. 注入预算、摘要上下文与非编程摘要格式按集成结果单独决定，不捆绑一个新的压缩框架。

## 考虑过的替代方案

**全面关闭 DSH 压缩。** 可避开交互，却使长对话直接遇到上下文上限，也失去宿主的工具配对与恢复机制，不作为默认方案。

**对摘要请求照常套完整预设。** 会让 assistant 前缀、正则或角色要求干扰摘要，还可能再次执行变量操作；保留用途隔离。

**从完整事件日志重建压缩前历史。** 会抵消压缩并复活图片或工具结果，不采用。

**仅清空编译缓存。** 当前消息变化已经会失效；额外清缓存既不能解决副作用，也不能修正摘要输入和预算。

## 验收与风险

使用虚构预设和假模型响应，优先做少量定向测试：

- 摘要请求保持原摘要指令、上限和流式设置，不注入预设、不运行动态提供者、不改变 local/global；与同会话活跃普通请求并行时也成立。
- 压缩后请求只带检查点与保留尾部，预设只注入一次；历史深度按新历史计算，旧正文不复活，工具调用/结果成组保持。
- 仅检查点或检查点加工具结果时，latestUser 不指向摘要；历史替换与正则默认不破坏检查点。
- 假模型先报上下文溢出、宿主压缩后重试成功，计数宏只按既定逻辑请求语义提交一次；新用户轮次和正常工具续步不被误去重。
- requestHeader 的 maxTokens、压缩输出预留与最终 Raw 一致；大静态预设超限有清楚失败结果。
- 插件停用、取消或提供者热重载不留下跨请求桥接设置；草稿预览不会提交变量。

当前只完成源码分析和纯函数检查，没有完成这些集成验收；尤其不把重试身份、异步作用域隔离或预算扩展点当成现成能力。
